# Wireshark Scenario 3: Web Scanner / Recon Detection (Nikto)

## Overview
This scenario captures and analyzes network traffic generated by a Nikto web vulnerability scan run from the attacker-side Kali VM against apache-web-01. It's a packet-level companion to the "Web Scanner - High 404 Recon Detection" alert built earlier in the Splunk SIEM project, confirming the same activity is visible — and just as clearly identifiable — at the raw traffic level.

## Environment
- **Attacker:** Kali Linux VM — `192.168.208.30`
- **Target:** apache-web-01 — `192.168.208.10`
- **Capture interface:** `eth1` (host-only segment, 192.168.208.0/24)
- **Capture tool:** `tcpdump`, analyzed in Wireshark

## Scan Execution
Traffic was captured on Kali's `eth1` interface while running:

```bash
sudo tcpdump -i eth1 -w nikto-scan.pcap
```

```bash
nikto -h http://192.168.208.10
```

Both the scan and the capture were left running, then stopped once a substantial volume of traffic had been generated. The resulting pcap was verified as readable before analysis:

```bash
tcpdump -r nikto-scan.pcap -c 10
```

## Observations

### 1. Rapid-fire GET requests against probe paths
Filtering on `http.request.method == "GET"` shows a dense stream of requests from `192.168.208.30` to `192.168.208.10`, spaced roughly 5–30ms apart — far faster than any human browsing pattern. Requested paths include Nikto's standard vulnerability-check probes: `/`, `/server-status`, `/icons/`, `/trace.axd`, `/nosuchfile.asp`, `/nosuchfile.aspx`, `/localstart.asp`, `/docs/`, `/webcgi/`, `/cgi-914/`, `/cgi-915/`. The sequential, incrementing naming (`/cgi-914/`, `/cgi-915/`) is characteristic of a tool grinding through an internal checklist rather than a person navigating a site.

### 2. Overwhelming 404 response rate
Filtering on `http.response.code` returned 7,760 HTTP responses (40.5% of the total 19,138-packet capture). Narrowing further to `http.response.code == 404` returned 7,489 responses (38.9% of the capture) — meaning **~96.5% of all HTTP responses in this capture were 404 Not Found**.

This closely matches the ~96% 404 rate observed in the equivalent Splunk detection for this same scan, confirming consistency between the log-level and packet-level views of the identical event.

**Note on the 404s:** the overwhelming majority reflect paths that were never going to exist on this install regardless of hardening — Nikto's check database probes for artifacts from many unrelated software stacks. A small subset (e.g. `/server-status`, `/server-info`) are exceptions where a 404 can reflect actual hardening from Project 1 (mod_status/mod_info disabled or restricted), rather than the path simply never existing.

### 3. Traffic volume as a signal on its own
HTTP traffic made up over 40% of the entire capture for what was, from the target's perspective, a single visitor — a strong standalone indicator of automated scanning activity even before looking at response codes or specific paths.

## Detection Takeaways
The same signal that drove the Splunk alert threshold (high request volume + high 404 rate from a single source in a short window) is directly visible in the raw packet capture:
- Request rate/timing (sub-30ms intervals) as a behavioral indicator
- 404 ratio (~96.5%) as a confirmatory indicator
- Single source/destination pair concentrating the activity

This reinforces that recon-stage scanning is detectable both at the log layer (SIEM) and the wire layer (packet capture) using the same underlying behavioral pattern — request rate and response-code distribution — regardless of which telemetry source is available.
